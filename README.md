# go-trends-aggregator

Сервис для виджета «Сейчас ищут»: считает топ поисковых запросов за последние
5 минут.

Я исходил из того, что API топа читают часто, а события в брокер пишет
сервис поиска. Поэтому сервис держит окно в памяти, раз в секунду пересобирает
топ в фоне, а HTTP handler отдаёт уже готовый результат — не считает ничего
на лету.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

После старта будут доступны:

- HTTP API — `http://localhost:8080`
- NATS — `nats://localhost:4222`
- NATS monitoring — `http://localhost:8222`

Проверка, что сервис жив:

```bash
curl http://localhost:8080/healthz
curl http://localhost:8080/readyz
```

При первом запуске топ пустой — данных ещё нет. Чтобы они появились, есть
отдельный генератор синтетических событий:

```bash
docker compose --profile load up --build
```

`loadgen` публикует события в JetStream. Сам stream он не создаёт — ждёт,
пока его создаст основной сервис, и только потом начинает писать.

## Примеры API

Получить топ:

```bash
curl "http://localhost:8080/v1/trends?limit=10"
```

Ответ:

```json
{
  "window_seconds": 300,
  "generated_at": "2026-05-26T10:30:00Z",
  "items": [
    {
      "rank": 1,
      "query": "iphone 15 pro",
      "score": 120
    }
  ]
}
```

`score` — это число уникальных голосов внутри окна по правилу «один actor +
один query = один голос». Если один и тот же пользователь 100 раз вбил
`iphone 15 pro`, в ранжировании это посчитается как 1, а не 100.

Если хочется увидеть «сырые» счётчики, можно попросить debug-режим:

```bash
curl "http://localhost:8080/v1/trends?limit=10&debug=true"
```

При `debug=true` к каждому элементу добавляется поле `raw` — счётчик всех
валидных событий, включая повторные голоса одного actor'а. Ранжирование от
этого не меняется, топ всё равно строится по `score`.

Стоп-лист — добавить термин:

```bash
curl -X POST http://localhost:8080/v1/stoplist \
  -H "Content-Type: application/json" \
  -d '{"term":"iphone 15 pro"}'
```

Посмотреть список:

```bash
curl http://localhost:8080/v1/stoplist
```

Удалить:

```bash
curl -X DELETE "http://localhost:8080/v1/stoplist/iphone%2015%20pro"
```

Метрики для Prometheus:

```bash
curl http://localhost:8080/metrics
```

Невалидный `limit` (например `limit=abc` или `limit=0`) возвращает
`400 Bad Request`.

## Контракт события

Сервис читает события из JetStream:

- stream — `SEARCH_EVENTS`
- subjects — `search.events.*`

Пример payload'а:

```json
{
  "event_id": "01HW8K3M5N7Q9R1T3V5X7Z9A1C",
  "query": "iPhone 15 Pro",
  "actor_id": "u_4571892",
  "session_id": "s_abc123",
  "timestamp": "2026-05-22T14:23:45.123Z"
}
```

Зачем каждое поле:

- **`event_id`** — идентификатор события. Сейчас я только проверяю, что он не
  пустой. Отдельной дедупликации по `event_id` (типа «уже видели этот id»)
  в этой версии нет, но поле обязательное в контракте — без него потом нельзя
  будет защититься от повторной обработки и нормально находить события в
  логах.
- **`query`** — собственно поисковый запрос, из него строится топ. Сервис сам
  нормализует строку (см. ниже), чтобы `iPhone 15 Pro` и `iphone 15  pro`
  считались одним запросом.
- **`actor_id`** — нужен для правила «один actor — один голос за один query
  внутри окна». Без этого поля невозможно отличить повторные клики одного
  пользователя от реального интереса разных людей, и топ легко накручивается.
- **`session_id`** — сейчас в расчёте не участвует. Я не стал убирать его из
  контракта, потому что он пригодится, если позже захотим добавить более
  серьёзные правила против ботов (например, лимит на сессию).
- **`timestamp`** — время события у источника. Окно я считаю по этому полю, а
  не по времени получения из брокера: брокер может задержаться, и тогда
  опоздавшее событие попадёт «не в ту секунду».

Нормализация `query`:

- Unicode NFC
- lowercase
- trim
- схлопывание подряд идущих пробелов в один
- замена `ё` → `е`
- ограничение длины 256 rune

## Архитектура

Поток данных:

```text
Search Service
    │
    ▼
NATS JetStream: search.events.*
    │
    ▼
Pull consumer (временный)
    │
    ▼
validate + normalize
    │
    ▼
bounded channel
    │
    ▼
Aggregator: ring buffer + sharded counters + seenVotes
    │
    ▼
горутина-snapshotter, раз в 1 секунду
    │
    ▼
atomic.Pointer[Snapshot]
    │
    ▼
HTTP /v1/trends
```

### Почему NATS JetStream

Я выбрал JetStream, потому что он легко поднимается через docker-compose и
при этом хранит сообщения на диске и умеет перечитывать историю — то есть
после рестарта сервиса я могу заново прочитать последние 5 минут событий. Kafka тоже подошла бы, но для
локального запуска в тестовом задании она тяжелее. RabbitMQ менее удобен
именно для перечитывания истории по времени, которое мне нужно для
восстановления окна.

### Consumer

Я делаю временного consumer'а (создаётся заново на каждый старт), а не
постоянного (durable). Постоянный запомнил бы последний ack'нутый offset и
продолжил бы с него — это плохо для моего случая: после рестарта мне нужно
перечитать ровно последние 5 минут окна, а не «продолжить с того места,
где остановился». Поэтому при старте сервис говорит JetStream «дай мне всё
за последние `WINDOW_DURATION + LATENESS_TOLERANCE`», и переигрывает окно
заново.

## Структуры данных

Главное, что должна уметь структура для топа:

1. Быстро инкрементить счётчики (события идут потоком).
2. Уметь «забыть» события старше 5 минут.
3. Быстро находить top-K по счётчику для ответа в API.

Я сделал три связанных штуки: ring buffer из bucket'ов, sharded глобальные
счётчики и отдельную map для anti-abuse правила.

### Ring buffer из bucket'ов

Окно 5 минут разбито на bucket'ы по 1 секунде — итого 300 ячеек в обычном
массиве. Каждый bucket хранит дельту счётчиков за свою секунду:

```go
countDelta  map[string]Counters  // что прибавили в эту секунду
votesIssued map[string]int64     // какие голоса выдали (для seenVotes)
epoch       int64                // секунда, к которой относится bucket
```

Зачем `countDelta`: когда bucket «выпадает» из окна, я вычитаю его дельту из
глобальных счётчиков. Это дешевле, чем каждый раз пересчитывать топ с нуля.

Зачем `epoch`: индексы в массиве переиспользуются каждые 300 секунд
(`bucketIndex = epoch % 300`). Без отдельного поля `epoch` я бы не смог
отличить bucket «12:00:05» от bucket «12:05:05» — у них один и тот же индекс
массива. При записи я сравниваю `epoch` и, если он устарел, сначала «выписываю»
старый bucket из глобальных счётчиков, а потом пишу новое значение.

### Глобальные счётчики

Отдельная map `query → Counters` с суммой за всё окно — это то, что отдаётся
в API. Я не стал делать одну большую map с одним мьютексом: тогда все
worker'ы и горутина-snapshotter дрались бы за один lock. Вместо этого
сделал 256 шардов по `hash(query)` — записи разных запросов идут параллельно,
почти не пересекаясь.

Число шардов (256) выбрано как простой дефолт для тестового стенда; на
реальной нагрузке его нужно подбирать по бенчмаркам.

`Counters` — это пара:

```go
Raw   int64  // все валидные события
Score int64  // только уникальные голоса
```

Топ строится по `Score`. `Raw` отдаётся в debug-режиме — полезно, чтобы
видеть, сильно ли запрос отличается «по реальным кликам» и «по уникальным
голосам» (косвенный признак накрутки).

### seenVotes

Чтобы один actor не мог накрутить топ повторными запросами, есть отдельная
sharded map:

```go
actor_id + query → expiresAt
```

При записи события я проверяю: если ключ уже есть и ещё не истёк — событие
увеличивает только `Raw`, но не `Score`. Если ключа нет — добавляю и
увеличиваю оба счётчика. Когда bucket «выпадает» из окна, я удаляю из
seenVotes ключи, которые в нём «жили», с проверкой `expiresAt` — чтобы не
снести случайно более свежий голос с тем же ключом.

### Snapshot

Раз в секунду отдельная горутина проходит по всем шардам счётчиков,
применяет стоп-лист и через min-heap собирает top-K. Результат кладётся в
`atomic.Pointer[Snapshot]`. HTTP handler ничего не считает — просто загружает
указатель и режет первые N элементов.

То есть на стороне API нет ни блокировок, ни обхода всех счётчиков — чтение
буквально стоит «загрузить указатель и скопировать N элементов». Если бы я
считал топ на каждый запрос, чтение стало бы узким местом.

## Стоп-лист

Стоп-лист меняется через HTTP без рестарта. Внутри он лежит в
`atomic.Pointer[map[string]struct{}]` с copy-on-write на запись:

- чтения — без мьютекса вообще, только `Load()`;
- запись — берём mutex, копируем map целиком, добавляем/удаляем элемент,
  атомарно подменяем указатель.

Я выбрал такую схему, потому что чтений стоп-листа много (по одному на каждый
запрос в map счётчиков при сборке snapshot'а), а изменений — редкие ручные
операции через API. Полное копирование map при записи — нормально, в
стоп-листе обычно сотни элементов, не миллионы.

Важный момент: стоп-лист применяется на этапе сборки snapshot'а, а не при
приёме события в агрегатор. Если бы я фильтровал на приёме, то уже
накопленные в окне события продолжали бы попадать в топ ещё 5 минут после
добавления слова в стоп-лист. С фильтрацией на snapshot новое слово
исчезает из топа максимум через 1 секунду (на следующей пересборке) — и для
уже накопленных, и для новых событий.

Минус — стоп-лист сравнивает строки точно. Если добавить `iphone`, то
`iphone 15 pro` всё равно попадёт в топ. Я сделал так сознательно: поиск по
подстроке слишком легко даёт ложные срабатывания (добавишь короткое слово —
и улетит куча нормальных запросов).

## Опоздавшие и будущие события

События берутся по `timestamp` из payload'а, а не по моменту получения. Это
значит, что у события есть «возраст»:

- старше окна — отбрасываются;
- из будущего (timestamp больше «сейчас») — тоже отбрасываются;
- в обоих случаях событие всё равно ack'ается в JetStream (иначе оно
  застрянет и будет приходить снова), но в метриках идёт как dropped.

Есть параметр `LATENESS_TOLERANCE` (по умолчанию 10 секунд). При старте
сервис переигрывает не ровно 5 минут, а `5 минут + 10 секунд`, чтобы
прихватить события, которые опоздали из-за задержки в брокере.

## Конфигурация

| Переменная | По умолчанию | Что значит |
| --- | --- | --- |
| `HTTP_ADDR` | `:8080` | адрес HTTP-сервера |
| `NATS_URL` | `nats://localhost:4222` | адрес NATS |
| `NATS_STREAM` | `SEARCH_EVENTS` | имя stream'а |
| `NATS_SUBJECTS` | `search.events.*` | subjects stream'а |
| `NATS_FILTER` | `search.events.*` | фильтр consumer'а |
| `NATS_FETCH_BATCH` | `500` | сколько сообщений забираем из NATS за один раз |
| `NATS_FETCH_TIMEOUT` | `100ms` | сколько ждём накопления пачки |
| `NATS_ACK_WAIT` | `30s` | сколько JetStream ждёт ack |
| `NATS_MAX_ACK_PENDING` | `10000` | максимум неподтверждённых сообщений в полёте |
| `WINDOW_DURATION` | `5m` | размер окна |
| `BUCKET_DURATION` | `1s` | размер одного bucket'а |
| `LATENESS_TOLERANCE` | `10s` | допустимое опоздание событий |
| `SNAPSHOT_INTERVAL` | `1s` | как часто пересобирается snapshot |
| `SHARD_COUNT` | `256` | число шардов в счётчиках и seenVotes |
| `MAX_TOP_LIMIT` | `1000` | максимум для `?limit=` в API |
| `QUEUE_CAPACITY` | `10000` | размер канала между consumer и worker'ами |
| `WORKER_COUNT` | `NumCPU()` | сколько worker'ов разбирают канал |

Числа в дефолтах выбраны как стартовые значения для тестового стенда. В
проде `MAX_ACK_PENDING`, `QUEUE_CAPACITY` и `SHARD_COUNT` точно надо тюнить
по реальной нагрузке.

## Метрики

Все на `/metrics`. Самые полезные на практике:

- `events_received_total` — сколько событий вообще пришло;
- `events_invalid_total` — отброшенные на валидации (пустое поле, кривой JSON);
- `events_dropped_total{reason=...}` — отброшенные из-за окна (expired/future);
- `events_duplicate_vote_total` — сколько раз сработало правило «один actor —
  один голос»;
- `agg_queue_depth` — сколько событий сейчас лежит в канале между consumer и
  worker'ами; если упирается в потолок — пора увеличивать `WORKER_COUNT`;
- `snapshot_age_seconds` — сколько секунд snapshot'у; используется в `/readyz`;
- `api_request_duration_seconds` — время ответа ручек.

Дополнительно есть метрики по JetStream pending, размеру стоп-листа и
длительности сборки snapshot'а — туда смотрят реже.

## Trade-offs и бизнес-логика

Здесь — на какие компромиссы я сознательно пошёл и какие моменты в постановке
были не описаны, как я их закрыл.

### Компромиссы ради производительности

**Состояние в памяти, без внешней БД.** Окно всего 5 минут, и пересчёт топа
должен быть быстрым. Поэтому я не пишу счётчики в Redis или Postgres — это
была бы сетевая задержка на каждое событие. После рестарта состояние
восстанавливается из JetStream replay'ем. Минус — во время рестарта API
недоступен, а после старта сервису нужно заново переиграть окно из
JetStream. Если JetStream недоступен или история уже удалена по `MaxAge`,
окно восстановится не полностью.

**Snapshot раз в секунду, а не пересчёт на каждый запрос.** Это значит, что
ответ API отстаёт от реальности максимум на 1 секунду. Для виджета «Сейчас
ищут» это нормально (пользователь не заметит), зато чтение становится
почти бесплатным — атомарный `Load()` и копирование N элементов. Если бы я
считал на каждый запрос, под нагрузкой это стало бы узким местом.

**Sharded counters вместо одной map с мьютексом.** Одна большая map с
мьютексом быстро стала бы узким местом при конкурентных записях — worker'ы
стояли бы в очереди за один lock. Шардирование по `hash(query)` решает это
просто. Цена — сборка snapshot'а обходит все шарды по очереди под RLock,
это чуть дороже, чем одна map, но запись не блокируется.

**Стоп-лист применяется на snapshot, а не на приёме события.** Так
изменение стоп-листа применяется сразу и к уже накопленным данным, а не
только к новым. Цена — горутина-snapshotter делает `Load()` стоп-листа и
проверку на каждый запрос в счётчиках. Стоп-лист обычно маленький, так что
поиск в map дешёвый.

### Что было неясно в постановке и как я решил

- **Какой payload приходит из брокера** — в задании не зафиксировано. Я
  предположил минимальный разумный набор: `event_id`, `query`, `actor_id`,
  `session_id`, `timestamp`. Обоснование каждого поля — выше.
- **Считать «последние 5 минут» по времени события или по времени обработки**
  — выбрал по времени события (поле `timestamp`). По времени обработки в
  топ бы попадали аномалии из-за задержек в брокере: replay за прошлый час
  превратился бы во «всплеск сейчас».
- **«Защита от аномальных всплесков»** — не было формализовано, что считать
  аномалией. Я сделал минимальное правило: один actor может дать только
  один голос за один query внутри окна. Это закрывает базовую проблему —
  один пользователь вбивает одно и то же много раз. От организованной
  накрутки (ботнет с разными `actor_id`) это, конечно, не защитит — для
  такого нужны отдельные сигналы (поведение, fingerprint, скорость).
- **Как часто должен обновляться виджет** — не было сказано. Я выбрал 1
  секунду как баланс: пользователь воспринимает это как «в реальном
  времени», а сервис не пересобирает топ слишком часто.
- **Как должен работать стоп-лист** — не было описано вообще. Я сделал
  динамический API (без рестарта) и точное сравнение по нормализованной
  строке. Поиск по подстроке — отдельная задача, в эту версию не добавлял.
- **Нужна ли персистентность состояния сервиса** — не было требований. На
  диск ничего не пишу: окно короткое, восстанавливается из JetStream.
- **Горизонтальное масштабирование** — явно не требовалось. В текущей
  версии оно не сделано для приёма событий (агрегатор один). Чтение
  масштабировать относительно несложно: snapshot можно раздавать инстансам,
  которые только отвечают на HTTP. Запись сложнее — нужны несколько
  агрегаторов по шардам и отдельный сборщик общего top-K, и в эту версию я
  этого делать не стал.

### Что бы добавил, если бы было больше времени

- LRU-дедуп по `event_id` для строгой защиты от дублей. JetStream гарантирует
  доставку «хотя бы один раз», то есть одно и то же событие может прийти
  дважды. Сейчас повторная доставка не увеличит `Score`, если actor уже
  голосовал за этот query, но `Raw` всё равно вырастет. Чтобы повтор
  игнорировался полностью, нужен отдельный LRU по `event_id`.
- Тесты на восстановление из JetStream после рестарта — сейчас этот сценарий
  я проверял только руками.
- Метрики p50/p99 на весь путь приёма события (от получения до записи в
  счётчики).
- Ограничение размера seenVotes сверху — если actor'ов очень много, map
  может разрастаться до момента ротации bucket'ов.
- Нагрузочное тестирование с `wrk`/`vegeta` и реальные цифры RPS/задержек
  в README, а не общие слова про «дешёвое чтение».
